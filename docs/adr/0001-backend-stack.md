# ADR 0001: 백엔드 스택 선택

- 상태: **Accepted** — 1일차 팀 논의에서 확정
- 날짜: 2026-09-02
- 관련 Issue: #
- 참여자: 손현아, 최인서, 문성도, 박상명, 박현수

## 배경

프런트엔드는 React + TypeScript로 정했다([ADR 0002](0002-frontend-stack.md)).
백엔드는 아직 정하지 못했고, **이 결정이
확정될 때까지 백엔드 개발자와 데이터 아키텍트가 손을 대지 못한다.**
1일차 안에 반드시 정해야 한다.

제약:

- 전체 일정이 **3일**이다. 세팅에 쓸 수 있는 시간이 반나절 남짓이다.
- 평가 대상은 완성도가 아니라 **설계 타당성과 스캐폴딩 완성도**다.
- 2일차에 **REST API 명세서**를 산출물로 내야 한다.
- AI 호출은 Mock이지만, **비동기 구조**(202 Accepted + 상태 폴링)를
  구조적으로 보여줘야 한다.
- 개발 PC에 **JDK가 설치되어 있지 않다.** (Node 24 / Python 3.14 / uv는 있음)

과정 자료가 허용한 선택지는 Spring Boot, FastAPI, Express 셋이다.

## 검토한 선택지

### A. Python / FastAPI

| | 내용 |
| --- | --- |
| 장점 | `async`/`await`가 기본이라 **Asynchronous Pipeline 원칙을 코드로 바로 보여준다**<br>Swagger UI가 `/docs`에 **자동 생성** → API 명세서 산출물이 공짜로 나온다<br>Pydantic 모델이 곧 JSON Schema → `07-ai-ready.md`의 스키마와 코드가 자동으로 일치<br>과정 자료가 "AI API 연동 친화적"으로 명시<br>`uv`가 이미 설치돼 있어 세팅이 몇 분이면 끝난다 |
| 단점 | 팀원이 Python에 익숙하지 않으면 진입 비용<br>프런트엔드(JS)와 언어가 달라 문맥 전환이 있다 |

### B. Java / Spring Boot

| | 내용 |
| --- | --- |
| 장점 | 엔터프라이즈 표준. 취업·실무 연결성이 높다<br>계층 구조(Controller–Service–Repository)가 강제돼 **구조 설명이 명확**하다<br>JPA로 ERD와 엔터티가 자연스럽게 대응된다 |
| 단점 | **JDK 설치부터 필요하다** — 팀원 전원의 환경을 맞추는 데 시간이 든다<br>Gradle 초기 빌드가 느려 3일 일정에서 체감 비용이 크다<br>Swagger는 springdoc 의존성 추가가 필요<br>비동기 처리를 보여주려면 `@Async` 등 추가 설정이 필요 |

### C. Node.js / Express

| | 내용 |
| --- | --- |
| 장점 | 프런트엔드와 언어 통일 → 팀원 전원이 양쪽을 읽을 수 있다<br>가장 가볍고 빠르게 뜬다 |
| 단점 | API 명세서를 **손으로 써야 한다** — 2일차 산출물 부담이 늘어난다<br>구조를 강제하지 않아 5명이 각자 다르게 짜면 발표 때 설명이 어려워진다 |

## 결정

**B. Java / Spring Boot 를 채택한다.**

고른 이유는 셋이다.

1. **계층 구조가 강제된다.** Controller-Service-Repository가 프레임워크 차원에서
   갈라지므로, 5명이 각자 짜도 구조가 흩어지지 않는다. 발표 4번 섹션의
   "프로젝트 폴더 구조 및 FE/BE 연동 상태 설명"을 그림 한 장으로 끝낼 수 있다.
2. **JPA 엔터티가 ERD와 1:1로 대응된다.** 설계 30점의 "ERD 테이블 관계 및
   정규화 타당성"을 코드로 그대로 보여줄 수 있다.
3. **실무 연결성.** 이 과정의 목표 직무와 가장 가깝다.

### 자바 버전은 21로 한다

**과정 자료는 자바 버전을 정해 주지 않았다.** PDF 8쪽에 `Java / Spring Boot`라고만
있다. 팀이 정한 것이므로 근거를 남긴다.

하한은 기술적으로 정해져 있다. **Spring Boot는 Java 17이 최소 요구사항이다** —
Boot 3에서 Java 8·11 지원이 끊겼다. 그래서 실제 선택지는 **17과 21(둘 다 LTS)** 이었다.

**21을 고른 이유는 가상 스레드(Virtual Threads)가 이 프로젝트의 주제와 맞닿아
있기 때문이다.**

이 프로젝트가 비동기 구조를 세우는 이유는 **AI 호출이 느리기 때문**이다
(AI-Ready 원칙 3: Asynchronous Pipeline). 지금은 Mock이라 즉시 끝나지만, 실제
LLM을 붙이면 요청 하나가 수 초씩 스레드를 붙잡는다. Java 21 + Spring Boot에서는
설정 한 줄로 이 비용이 크게 낮아진다. **`application.properties`에 이미 켜 뒀다.**

```properties
spring.threads.virtual.enabled=true
```

**발표 5번 섹션(향후 AI 실제 결합 시 로드맵)에 쓸 거리가 하나 생긴다** —
*"AI를 붙였을 때 동시 요청을 어떻게 감당할 것인가"* 에 대한 답을 스택 선택
단계에서 이미 마련해 뒀다고 말할 수 있다. 17을 골랐다면 이 답이 없다.

부차적으로 21이 더 오래 지원되고, 실무도 21로 옮겨 가는 중이다.

### Spring Boot 버전은 4.1.1이다 — 고른 것이 아니라 강제된 것이다

**이 결정을 내릴 때는 Spring Boot 3을 쓸 생각이었다.** 문서에도 그렇게 적혀 있었다.
그런데 스캐폴딩 단계에서 `start.spring.io`가 3.x를 **거부한다**는 것이 드러났다.

```text
Invalid Spring Boot version '3.5.9', Spring Boot compatibility range is >=4.0.0
```

생성기가 주는 것은 4.0.8과 4.1.1뿐이다. 3.x는 목록에 없다. 그래서 **4.1.1**로 간다.
`build.gradle`을 손으로 고쳐 3.x를 박을 수는 있지만, 생성기가 지원하지 않는 조합을
3일짜리 프로젝트에서 떠안는 것은 이득이 없다고 봤다.

**Boot 4가 Boot 3과 다른 점 중 우리에게 걸린 것**은 아래 셋이고, 전부 확인해서
해결했다. 자세한 내용은 [`backend/README.md`](../../backend/README.md)의
"이 스택에서 밟기 쉬운 함정".

| 다른 점 | 결과 |
| --- | --- |
| `spring-boot-starter-web` → **`-webmvc`** 로 개명 | 의존성 이름을 바꿔 반영 |
| `META-INF/spring.factories` 지원 제거 | `spring-dotenv`가 조용히 무효가 된다. Gradle이 `.env`를 직접 읽게 바꿈 |
| — | springdoc 2.8.6은 Boot 3용이지만 **실제 요청으로 동작을 확인했다.** `/v3/api-docs`와 Swagger UI 모두 정상 |

> 이 절은 결정을 뒤집는 것이 아니라 **같은 결정(Java + Spring Boot)의 버전이
> 외부 사정으로 정해졌다는 기록**이다. 그래서 새 ADR을 만들지 않고 여기에 남긴다.

### 21이 지불하는 비용

| 비용 | 대응 |
| --- | --- |
| 검색해서 나오는 예제가 17 기준이 더 많다 | 우리가 쓰는 범위(Web·JPA·REST)에서는 17과 21의 코드가 다르지 않다. 실제로 막히는 일은 거의 없다 |
| 가상 스레드는 Boot 3.2 이상이 필요하다 | 우리가 쓰는 Boot 4.1.1은 이 조건을 넘는다 |

이미 JDK 17만 설치된 팀원이 있어도 손으로 맞출 필요 없다. `build.gradle`의
`java.toolchain`이 컴파일을 21로 고정하므로 **전원이 같은 바이트코드로 돌고**,
21이 없으면 foojay 플러그인이 받아 온다. (절차는
[README 7단계](../../README.md))

### 이 선택이 지불하는 비용

배경에 적은 제약(개발 PC에 JDK 없음)을 감수하고 고른 것이다. **감수한다는 것을
여기 적어 두어야 나중에 "몰랐다"가 되지 않는다.**

| 비용 | 대응 |
| --- | --- |
| JDK 21 설치 필요 | 1일차에 **가장 먼저** 끝낸다. 이게 밀리면 전부 밀린다. 버전은 `build.gradle`의 `java.toolchain`으로 21에 고정한다 |
| Gradle 초기 빌드가 느리다 | 첫 빌드를 각자 미리 돌려 둔다. 발표 당일에 처음 받지 않는다 |
| Swagger가 기본 제공되지 않는다 | `springdoc-openapi-starter-webmvc-ui` 의존성을 추가한다 |
| 비동기 구조에 설정이 필요하다 | AI 확장 지점은 Mock이므로 `@Async` 없이도 된다. `202 Accepted` 즉시 반환 + 상태 조회 **구조**만 지키면 원칙 3을 만족한다 |

### 고르지 않은 선택지에 대해

발표 Q&A 대비로 남긴다.

- **FastAPI를 안 고른 이유** — 세팅은 더 빠르지만, 프런트엔드를 TypeScript로
  가져가면서 백엔드까지 Python이면 팀 안에 언어가 셋이 된다. 3일 일정에서
  문맥 전환 비용이 이득보다 크다고 봤다.
- **Express를 안 고른 이유** — API 명세서를 손으로 써야 해서 2일차 산출물
  부담이 늘고, 구조를 강제하지 않아 5명이 각자 다르게 짤 위험이 있다.
