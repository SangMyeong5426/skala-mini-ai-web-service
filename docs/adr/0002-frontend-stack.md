# ADR 0002: 프런트엔드 스택 선택

- 상태: **Accepted** — 1일차 팀 논의에서 확정
- 날짜: 2026-09-02
- 관련 Issue: #
- 참여자: 손현아, 최인서, 문성도, 박상명, 박현수

## 배경

저장소 초기 세팅에서는 프런트엔드를 **Vue 3 + Vite**로 잡아 두었다. 과정 자료
(`Project Tool Guide`, PDF 8쪽)의 Full-Stack Scaffolding 표에 프런트엔드 항목이
**Vue.js (Vite)** 와 **HTML/CSS/JS** 두 가지로 제시돼 있기 때문이다.

1일차 논의에서 이를 **React + TypeScript**로 바꾸기로 했다. 초기 세팅을 뒤집는
결정이고 팀 전체에 영향을 주므로 ADR로 남긴다.

제약:

- 전체 일정이 **3일**이다.
- 평가 대상은 완성도가 아니라 **설계 타당성과 스캐폴딩 완성도**다.
- 구현 범위는 **핵심 화면 1~2개**다. (PDF 6쪽, 2일차)
- 백엔드는 Spring Boot로 확정했다. ([ADR 0001](0001-backend-stack.md))

## 검토한 선택지

### A. Vue 3 + Vite

| | 내용 |
| --- | --- |
| 장점 | **과정 자료가 명시한 스택이다** — 평가가 "수업 내용과의 일관성"을 볼 때 안전<br>학습 곡선이 완만해 1~2개 화면이면 빠르게 나온다<br>저장소 초기 세팅이 이미 이쪽으로 잡혀 있다 |
| 단점 | 팀원의 사전 경험이 React 쪽에 몰려 있다 |

### B. React + TypeScript (Vite)

| | 내용 |
| --- | --- |
| 장점 | 팀원 다수가 이미 경험이 있어 **화면 구현 속도가 빠르다**<br>TypeScript 타입이 `06-api-spec.md`의 응답 규격과 **1:1로 대응**된다 — Interface First 원칙을 코드로 보여줄 수 있다<br>`07-ai-ready.md`의 출력 JSON Schema를 타입으로 옮겨 두면, 나중에 실제 LLM이 스키마를 어겼을 때 컴파일 단계에서 드러난다<br>생태계가 넓어 막혔을 때 검색으로 풀린다 |
| 단점 | **과정 자료의 스택 목록에 없다** — 아래 위험 항목 참조<br>Vue보다 초기 보일러플레이트가 많다 |

### C. HTML/CSS/JS (프레임워크 없음)

| | 내용 |
| --- | --- |
| 장점 | 가장 가볍다. 화면이 1~2개뿐이면 충분하다 |
| 단점 | 상태 관리와 폴링을 손으로 짜야 한다<br>발표 4번 섹션에서 보여줄 "프로젝트 구조"가 빈약해진다 |

## 결정

**B. React + TypeScript (Vite) 를 채택한다.**

고른 이유는 둘이다.

1. **팀원의 사전 경험이 여기 있다.** 3일 일정에서 학습 시간을 쓰지 않는 쪽이
   문서와 발표에 시간을 더 쓸 수 있다.
2. **TypeScript 타입이 AI-Ready 원칙 1(Interface First)의 증거가 된다.**
   `07-ai-ready.md`의 출력 스키마를 타입으로 선언해 두면, *"백엔드가 Mock에서
   실제 LLM으로 바뀌어도 프런트엔드는 이 타입을 그대로 쓴다"* 를 코드로 보여줄
   수 있다. 발표 2번 섹션의 핵심 주장을 말이 아니라 파일로 증명하는 셈이다.

### 검토했던 위험 — 해소됨

과정 자료(PDF 8쪽)의 프런트엔드 항목에는 **Vue.js와 HTML/CSS/JS만** 적혀 있어서,
평가가 수업 내용과의 일관성을 전제로 한다면 감점 여지가 있다고 봤다.

**1일차에 확인한 결과 React 사용이 가능하다.** 이 위험은 해소됐다.

다만 발표 Q&A에서 *"왜 자료에 없는 걸 썼나"* 는 나올 수 있다. 답은 위 "고른 이유"
2번이다 — **TypeScript 타입을 API 규격의 사본으로 두어 Interface First 원칙을
말이 아니라 파일로 증명하기 위해서다.** 프레임워크 취향이 아니라 설계 원칙을
보여주려고 고른 것이라는 점을 분명히 한다.
