## Actor

**Actor는 사람만이 아니다.** 외부 시스템도 Actor다. 이 서비스는 외부 Actor가
셋이고, **그중 둘이 AI 확장 지점과 맞닿아 있다.** 아래 표가 곧
"AI가 어디로 들어오는가"의 그림이 된다.

| Actor | 구분 | 설명 | 주요 목적 |
| --- | --- | --- | --- |
| **회원** | 사람 | 계정을 만든 여행 준비자. 페르소나 1~4가 여기 해당 | 빠짐없이 짐을 싸고, 공항에서 문제를 만나지 않는다 |
| **비회원** | 사람 | 로그인 없이 임시 모드로 쓰는 사용자 | 반입 규정만 빠르게 확인한다 |
| **AI 서비스** | 외부 시스템 | 준비물 추천 · 사진 물품 인식 · 무게 추정 · 자연어 응답.<br>**지금은 Mock, 나중에 실제 LLM·비전 모델** | 사람이 하기 반복적이고 규칙이 흐릿한 판단을 대신한다 |
| **규정 데이터 출처** | 외부 시스템 | 인천국제공항 · 항공정보포털의 공식 반입 기준 | 판정의 근거를 제공한다 |
| **날씨 서비스** | 외부 시스템 | Open-Meteo. 16일 예보 + 계절 예보 | 여행 시점의 기온·강수를 제공한다 |

> **규칙 엔진은 Actor가 아니다.** 시스템 내부 구성요소다. 반입 판정의 최종
> 책임은 규칙 엔진에 있고 AI에 있지 않다 — 이 구분이 이 서비스 설계의 핵심이라
> 4절에 따로 정리했다.

## 주요 Use-Case 상세

**AI 확장 지점이 있는 넷**과 그 앞뒤를 잇는 UC-02·UC-07을 채웠다.

### UC-02: 여행 등록

| 항목 | 내용 |
| --- | --- |
| Actor | 회원, 비회원 |
| 사전 조건 | 로그인했거나 비회원 임시 모드를 선택했다 |
| 기본 흐름 | 1. 새 여행 등록 화면에서 일정·출발지·도착지·목적·이동수단을 입력한다<br>2. 항공 이용이면 항공사·출발/도착 공항을 추가로 입력한다<br>3. 선택 항목(경유지·숙소·가방 크기·동행인·특이사항)을 입력한다<br>4. 시스템이 날짜 순서와 필수값 누락을 검증한다<br>5. 여행을 저장하고 체크리스트 생성 화면으로 이동한다 |
| 대체·예외 흐름 | · 귀국일이 출발일보다 빠르면 날짜 수정을 요청한다<br>· 필수값이 비면 해당 입력칸으로 이동시키고 강조한다<br>· 여행지가 검색되지 않으면 도시명 직접 입력을 허용한다<br>· 항공사·경유지를 비우면 **일반 기준만 적용되고 정확도가 낮아진다는 것을 표시**한다 |
| 사후 조건 | 여행 프로필이 저장되고 추천·규정 조회의 입력이 된다 |
| 관련 API | `POST /api/trips` → `201 Created` |
| 관련 화면 | `S-03` 여행 등록 |

### UC-03: 맞춤 체크리스트 생성 · **AI 확장 지점**

| 항목 | 내용 |
| --- | --- |
| Actor | 회원 ↔ **AI 서비스**, 날씨 서비스 |
| 사전 조건 | 여행 등록(UC-02)이 완료되었다 |
| 기본 흐름 | 1. 시스템이 여행 정보와 예상 날씨를 불러온다<br>2. **AI 작업을 접수하고 즉시 작업 ID를 돌려준다** (`202 Accepted`)<br>3. 화면은 "생성 중" 상태를 표시하고 **폴링**한다<br>4. AI가 여행 목적·기간·장소·계절을 해석해 준비물 후보를 만든다<br>5. 시스템이 여권 등 **고정 필수 규칙으로 결과를 보강**한다<br>6. 카테고리별(서류·의류·전자기기·세면용품·의약품·현지 맞춤)로 정리해 표시한다<br>7. 사용자가 추가·수정·삭제 후 확정한다 |
| 대체·예외 흐름 | · **출발일이 16일을 넘으면 예보가 없다.** 계절 평균을 쓰고 *"실시간 예보가 아님"* 을 표시한다<br>· 날씨 조회 실패 시에도 계절 평균으로 진행한다<br>· 여행 목적이 불명확하면 관광·출장·휴양 중 선택을 요청한다<br>· **AI 생성 실패 시 기본 체크리스트를 제공**하고 직접 편집하게 한다<br>· 의료 관련 추천은 **전문 진단처럼 표현하지 않는다** |
| 사후 조건 | 여행별 기본 체크리스트가 저장된다 |
| 관련 API | `POST /api/ai-jobs` (`job_type: PACKING_LIST`) → `202`<br>`GET /api/ai-jobs/{id}` → `200` (`PENDING` / `COMPLETED` / `FAILED`) |
| 관련 화면 | `S-04` 체크리스트 |

### UC-06: 사진 속 물품 인식 · 승인 · **AI 확장 지점**

| 항목 | 내용 |
| --- | --- |
| Actor | 회원 ↔ **AI 서비스** |
| 사전 조건 | 검수 가능한 사진이 한 장 이상 등록되었다 (UC-05) |
| 기본 흐름 | 1. **AI 작업을 접수하고 작업 ID를 돌려준다** (`202 Accepted`)<br>2. 화면은 "분석 중" 상태를 표시하고 **폴링**한다<br>3. AI가 사진에서 물품 후보·예상 수량·**신뢰도**를 만든다<br>4. 여러 장에 걸친 **동일 물품 후보를 하나로 묶는다**<br>5. 신뢰도가 낮거나 후보가 여럿이면 **"확인 필요"** 로 분류한다<br>6. 사용자가 이름·수량을 수정하거나 승인한다<br>7. **승인된 물품만** 다음 단계(UC-07·UC-08·UC-09)로 넘어간다 |
| 대체·예외 흐름 | · 식별 실패 시 사용자가 물품명을 직접 입력한다<br>· 중복 탐지는 묶어서 수량을 확정하게 한다<br>· 라벨 판독 실패 시 용량·배터리 정보를 직접 입력받는다<br>· **분석 중 화면을 벗어나도 결과는 저장된다** |
| 사후 조건 | 사용자 승인 물품 목록이 확정된다 |
| **AI가 하지 않는 것** | **용량·무게·배터리 정격·날 길이처럼 사진에 보이지 않는 속성은 추정하지 않는다.** 라벨 촬영이나 직접 입력을 요청한다 |
| 관련 API | `POST /api/ai-jobs` (`job_type: BAG_CHECK`) → `202`<br>`GET /api/ai-jobs/{id}` → `200` |
| 관련 화면 | `S-06` 인식 결과·승인 |

### UC-07: 준비물 비교 · 검수

| 항목 | 내용 |
| --- | --- |
| Actor | 회원 |
| 사전 조건 | 확정 체크리스트(UC-03·04)와 승인 물품(UC-06)이 모두 있다 |
| 기본 흐름 | 1. 체크리스트 항목과 승인 물품을 이름·카테고리 기준으로 대조한다<br>2. 일치하면 **준비 완료** 로 표시한다<br>3. 유사하나 확정할 수 없으면 **확인 필요** 로 표시한다<br>4. 사진에서 찾지 못하면 **"사진에서 미확인"** 으로 표시한다<br>5. 체크리스트에 없는데 사진에 있으면 **추가 물품** 으로 표시한다<br>6. 사용자가 각 상태를 최종 확인한다 |
| 대체·예외 흐름 | · 물품명이 다르면 유사 후보를 제시하고 사용자가 연결한다<br>· 사진 밖에 둔 물건은 사용자가 직접 완료 처리한다<br>· 예상 수량과 인식 수량이 다르면 둘 다 보여주고 확인을 요청한다 |
| 사후 조건 | 최종 준비 상태가 확정된다 |
| **이 서비스의 원칙** | **사진에서 찾지 못한 것을 "누락"으로 단정하지 않는다.** 반드시 *"사진에서 미확인"* 이라고 표현한다. 사진은 가방 전체를 본 것이 아니기 때문이다 |
| 관련 API | `PATCH /api/trips/{tripId}/items/{itemId}` → `200` |
| 관련 화면 | `S-07` 검수 결과 |

### UC-08: 예상 무게 산정 · **AI 확장 지점**

| 항목 | 내용 |
| --- | --- |
| Actor | 회원 ↔ **AI 서비스** |
| 사전 조건 | 사용자가 승인한 물품 목록(UC-06)이 있다 |
| 기본 흐름 | 1. 가방 종류·크기·빈 무게를 입력받는다 (선택: 제품 모델, 실측값, 항공사 한도)<br>2. **AI 작업을 접수하고 작업 ID를 돌려준다** (`202 Accepted`)<br>3. 품목별 **최소·대표·최대** 무게 범위를 합산한다<br>4. 가림·미식별 비율에 따라 **신뢰도(높음·보통·낮음)** 를 조정한다<br>5. 총중량 범위·품목별 기여도·**계산에서 제외한 항목**을 표시한다<br>6. 항공사 한도와 비교해 **여유 / 근접 / 초과 가능성** 을 표시한다<br>7. 물품·수량을 고치면 즉시 재계산한다 |
| 대체·예외 흐름 | · **승인 전 후보와 미식별 품목은 합계에 넣지 않고 제외 개수를 표시**한다<br>· 실측값이 있으면 추정값보다 **우선 적용**하고 원본 추정값과 구분해 저장한다<br>· 책·금속·배터리·카메라·액체는 오차가 커서 모델·용량·실측값을 먼저 요청한다<br>· 닫힌 가방이나 심한 겹침은 **계산을 중단하고 재촬영을 요청**한다<br>· 한도에 근접하면 확정 초과로 말하지 않고 **저울 측정을 권고**한다 |
| 사후 조건 | 예상 무게 범위와 신뢰도가 저장된다. **실측값과는 구분해서 저장한다** |
| **고정 안내 문구** | *"본 결과는 사진과 일반 중량 데이터를 이용한 참고용 추정치입니다. 탑승 전 실제 저울로 측정하고 해당 항공사의 최신 허용 기준을 확인해야 합니다."* |
| 관련 API | `POST /api/ai-jobs` (`job_type: WEIGHT_ESTIMATE`) → `202`<br>`GET /api/ai-jobs/{id}` → `200` |
| 관련 화면 | `S-07` 검수 결과 (무게 영역), `S-08` 무게 상세 |

### UC-09: 항공 반입 규정 확인

| 항목 | 내용 |
| --- | --- |
| Actor | 회원 ↔ 규정 데이터 출처 |
| 사전 조건 | 항공 여행 정보와 확인할 물품이 등록되어 있다 |
| 기본 흐름 | 1. **AI가 사진·질문에서 물품명을 구조화한다** (여기까지만 AI)<br>2. 판정에 필요한 세부정보(용량·배터리 Wh·날 길이·분리 여부)가 있는지 검사한다<br>3. 부족하면 라벨 사진 또는 직접 입력을 요청한다<br>4. **규칙 엔진이 공식 규정과 입력값을 비교한다**<br>5. 반입 구분·판단 근거·확인 날짜·최종 확인 경로를 표시한다 |
| 대체·예외 흐름 | · 규정을 확인할 수 없으면 **판정을 보류**하고 항공사 확인 경로를 준다<br>· 노선별 기준이 충돌하면 **더 엄격한 쪽을 우선 경고**하고 최종 확인이 필요함을 표시한다<br>· 세부정보가 부족하면 단정하지 않고 **"추가정보 필요"** 상태로 둔다 |
| 사후 조건 | 물품별 반입 상태와 근거가 저장된다 |
| 결과 상태 (6종) | `기내 반입 가능` · `위탁수하물 가능` · `위탁수하물 금지` · `반입 제한` · `추가정보 필요` · `항공사 확인 필요` |
| **AI와 규칙 엔진의 경계** | **최종 분류는 규칙 엔진이 한다.** AI는 물품명을 이해하고 설명을 생성할 뿐이다 |
| 관련 API | `GET /api/rules?transport=&keyword=` → `200`<br>`POST /api/ai-jobs` (`job_type: RULE_CHECK`) → `202` |
| 관련 화면 | `S-07` 검수 결과 (반입 영역), `S-09` 반입 규정 상세 |

### UC-10: 수하물 확인 챗봇 · **AI 확장 지점**

| 항목 | 내용 |
| --- | --- |
| Actor | 회원, 비회원 ↔ **AI 서비스** |
| 사전 조건 | 여행 정보가 있거나, 대화 중 출발지·도착지·항공사를 입력한다 |
| 기본 흐름 | 1. 질문에서 물품명과 여행 조건을 추출한다<br>2. 판정에 필요한 정보가 부족한지 확인한다<br>3. 부족하면 **한 번에 하나씩** 추가 질문한다<br>4. 규칙 엔진을 호출해 판정을 받는다<br>5. 결론·이유·권장 행동·**공식 출처·확인 날짜**를 함께 답한다 |
| 대체·예외 흐름 | · 질문 의도가 불명확하면 선택지를 제시한다<br>· 사진만으로 사양 확인이 안 되면 라벨 촬영·직접 입력을 요청한다<br>· 규정 출처에 문제가 있으면 일반 안내만 하고 항공사 확인을 요청한다<br>· **긴 대화에서도 이전 여행과 현재 여행의 조건을 섞지 않는다** |
| 사후 조건 | 대화 이력과 판정 근거가 저장된다 |
| 관련 API | `POST /api/ai-jobs` (`job_type: RULE_CHECK`) → `202`<br>`GET /api/ai-jobs/{id}` → `200` |
| 관련 화면 | `S-10` 챗봇 |

## Use-Case 사이 관계

다이어그램에는 넣지 않았다. `include`·`extend` 화살표를 다 그리면 선이 교차해서
읽을 수 없다. **관계는 여기서 관리한다.**

| 관계 | 뜻 |
| --- | --- |
| UC-03 `include` UC-02 | 체크리스트를 만들려면 여행 정보가 있어야 한다 |
| UC-06 `include` UC-05 | 물품을 인식하려면 사진이 등록돼 있어야 한다 |
| UC-07 `include` UC-04 | 비교하려면 확정된 체크리스트가 있어야 한다 |
| UC-07 `include` UC-06 | 비교하려면 승인된 인식 결과가 있어야 한다 |
| UC-08 `include` UC-06 | 무게를 재려면 승인된 물품 목록이 있어야 한다 |
| UC-09 `extend` UC-07 | 검수 중 반입 확인이 필요할 때만 이어진다 |
| UC-01 `extend` UC-02 | 과거 여행을 복사해 새 여행을 시작할 수 있다 |
| UC-10 | **어느 화면에서도 독립적으로 호출된다.** 비회원도 쓸 수 있다 |

## AI 확장 지점 정리

여기 적은 것이 [`07-ai-ready.md`](07-ai-ready.md)의 입력이 된다.

| Use-Case | `job_type` | 지금 (1~3일차) | 나중 (AI 결합 후) | 바뀌는 곳 |
| --- | --- | --- | --- | --- |
| UC-03 체크리스트 생성 | `PACKING_LIST` | Mock이 고정 JSON 반환 | LLM이 같은 스키마의 JSON 생성 | **백엔드 내부만** |
| UC-06 사진 물품 인식 | `BAG_CHECK` | Mock이 고정 인식 결과 반환 | 비전 모델이 같은 스키마로 반환 | **백엔드 내부만** |
| UC-08 예상 무게 산정 | `WEIGHT_ESTIMATE` | Mock이 고정 범위 반환 | 품목 중량 DB + LLM 보정 | **백엔드 내부만** |
| UC-09·UC-10 반입 규정 | `RULE_CHECK` | Mock이 고정 판정 반환 | LLM이 물품명 구조화, 규칙 엔진이 판정 | **백엔드 내부만** |

> 이 표의 마지막 칸이 핵심이다. **"백엔드 내부만 바뀐다"** 고 말할 수 있어야
> AI-Ready 설계가 성립한다. 프런트엔드나 API 규격이 함께 바뀌어야 한다면
> 그 설계는 AI-Ready가 아니다.

**엔드포인트는 넷이 아니라 하나다.** `POST /api/ai-jobs` 하나에 `job_type`으로
종류를 구분한다. 그래서 AI 작업이 늘어도 **엔드포인트가 늘지 않는다.**
근거는 [ADR 0003](adr/0003-ai-job-endpoint.md).

## AI · 규칙 엔진 · 사용자의 책임 경계

**발표에서 가장 많이 질문받을 표다.** Notion 기능 정의 5절을 옮겼다.

| 주체 | 담당 범위 | 하지 않는 것 |
| --- | --- | --- |
| **생성형 AI** | 준비물 추천, 자연어 설명, 질문 의도 파악, 결과 요약 | 공식 규정의 **최종 판정**과 실제 무게를 확정하지 않는다 |
| **이미지 AI · OCR** | 물품 후보, 수량, 라벨 정보, 사진 품질·신뢰도 추정 | **보이지 않는 속성을 추측해 확정**하거나, 승인 전 결과를 최종 상태로 쓰지 않는다 |
| **규칙 엔진** | 버전 관리된 공식 규정과 사용자 조건의 일관된 비교 | 필수정보가 없거나 규정이 충돌하면 **확정 판정을 만들지 않는다** |
| **사용자** | 물품·수량·실측값 승인, 실제 준비 여부와 최종 반입 여부 확인 | 서비스 결과만으로 출발 당일 항공사·보안검색기관 판단을 대체할 수 없다 |

## 원본 명세의 불일치와 팀 확정 사항

Notion 「기능 정의」 안에서 서로 어긋나는 곳이 있었다. **아래대로 확정했다.**
Notion 문서를 고칠 때도 이 기준을 따른다.

### ① 기능 번호 — **4절 상세 기능 표를 정본으로 한다**

| 위치 | 무게 | 챗봇 | 재사용 |
| --- | --- | --- | --- |
| **4절 상세 기능 표** ← **정본** | **`F-10`** | **`F-08`** | **`F-09`** |
| 6절 제목 | `F-11` | — | — |
| 4절 F-04 예외 문구 | `F-11` | — | — |
| 8절 로드맵 | `F-11` | `F-09` | `F-10` |

4절만 한 칸 당겨져 있고 나머지가 안 따라왔다. **4절이 가장 완전한 표라 이쪽을 택했다.**
Notion의 6절 제목과 8절 로드맵은 `F-10`(무게)·`F-08`(챗봇)·`F-09`(재사용)로 고쳐야 한다.

### ② 사진과 체크리스트의 선후 — **체크리스트가 먼저다**

3절 「전체 서비스 흐름」의 순서를 따른다.

```
③ 체크리스트 생성(추천)  →  ④ 사진 등록  →  ⑤ 물품 인식  →  ⑦ 목록 비교
```

4절 F-05 목적 문구 *"이미지 인식을 통해 확인된 물품 체크리스트에 등록 및 여행 조건에
맞는 준비물을 빠짐없이 제안한다"* 는 **두 시점을 한 문장에 합친 것으로 읽었다.**
뒤쪽(준비물 제안)이 ③이고, 앞쪽(인식 결과를 체크리스트에 반영)은 ⑦ 목록 비교에 해당한다.

**이 순서가 아니면 UC-07 「준비물 비교」가 성립하지 않는다.** 대조할 목록이 없기 때문이다.

### ③ 오타

1절 핵심 원칙 끝의 `제공한다.x`, 페르소나 1 이용 흐름의 `여행 등록보 등록 →
맞춤 체크리스트 생성 생성보 생성`. **Notion에서 고쳐야 한다.**
